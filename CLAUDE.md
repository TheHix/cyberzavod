# Киберзавод

Сайт-витрина: изометрический цех в браузере проигрывает записи того, как ИИ-агенты собирают этот же проект. Код открытый, сайт для портфолио. Домен — cyberzavod.com.

Правила конкретных частей лежат рядом с кодом: `apps/web/CLAUDE.md`, `apps/api/CLAUDE.md`, `packages/core/CLAUDE.md`.

## Команды

- `make check` — все проверки: типы, тесты, сборка фронта и API, сборка Docker-образа. CI вызывает те же make-цели. Должна проходить перед любым коммитом.
- `make dev` — Postgres и API в Docker, фронт с горячей перезагрузкой на http://localhost:4321.
- `make up` / `make down` — поднять или остановить Docker-окружение.
- `make server-bootstrap` — привести VPS к состоянию из `deploy/` (идемпотентно, нужен SSH-алиас `cyberzavod`).
- `make help` — остальные команды.

Если работаешь в dev-контейнере (`DEVCONTAINER=true`, см. `.devcontainer/README.md`): Docker и доступа к серверу там нет намеренно. Перед коммитом — `make check-web check-api`, проверки с Docker выполнит CI. API — `make api-dev`, сайт — `pnpm dev --host`.

## Устройство

Монорепозиторий: pnpm workspaces для TypeScript, отдельный Go-модуль для API.

- `packages/core` — ядро завода на чистом TypeScript: формат записи сборки, счётчики, дальше проигрыватель.
- `apps/web` — сайт: Astro + SolidJS, слои FSD, цех на canvas через PixiJS.
- `apps/api` — API на Go с Postgres.
- `compose.yaml` — локальное окружение: db → migrate → api.
- `deploy/` — продакшен: compose для сервера, nginx на хосте, скрипты деплоя и бэкапа. Как это работает — `deploy/README.md`.

Деплой автоматический: push в `main` → проверки → образы в GHCR с тегом sha → выкатка на сервер. Всё, что настроено на сервере, описано в `deploy/`; руками на сервере ничего не меняем.

Цех рисует только то, что выводится из событий записи. Новое визуальное состояние начинается с нового типа события в `packages/core`.

## Качество кода

Код должен читаться как описание того, что он делает, и расширяться добавлением, а не правкой по всему проекту. Конкретно:

- **Имена из предметной области.** Запись, сборка, этап, цех, возврат — а не `data`, `item`, `handle`, `process`. Без сокращений, кроме общепринятых (`ctx`, `err`, `id`).
- **Одна функция — одно действие.** Если функцию нельзя назвать без «и», её надо разделить. Тело читается сверху вниз без прыжков: сначала ранние выходы, потом основной путь.
- **Расширение через типы, а не через условия.** Новый вариант — новый член размеченного объединения (TS) или новая реализация интерфейса (Go). Ветвление по варианту — исчерпывающий `switch`, где пропущенный случай ловит компилятор, а не цепочка `if` по строкам в разных файлах.
- **Абстракция — когда появился второй реальный случай.** Не заводить интерфейс, фабрику или параметр «на будущее».
- **Зависимости направлены внутрь.** Ядро ничего не знает о сайте и API; бизнес-логика не знает о фреймворке, базе и HTTP — только об интерфейсах.
- **Ошибки не глотаются.** Либо обработать, либо вернуть с контекстом (`fmt.Errorf("загрузка миграций: %w", err)`, свой класс ошибки в TS).
- **Комментарий объясняет «почему»**, когда это не видно из кода. Пересказ кода словами, закомментированный и мёртвый код не допускаются.
- **Без магических значений.** Числа и строки со смыслом получают имя.

## Тесты

- Новая логика — с тестом рядом.
- Каждый тест — три блока **Arrange / Act / Assert**, помеченные комментариями `// Arrange`, `// Act`, `// Assert` и разделённые пустой строкой. Если готовить нечего, `// Arrange` опускается.
- Act — ровно одно действие над проверяемым кодом. Для проверки исключения действие оборачивается в функцию: `const act = () => parse(raw);`, затем `assert.throws(act, …)`.
- Одно поведение на тест, название теста — это поведение по-русски: «время не может идти назад».
- Табличные тесты в Go: подготовка данных — в таблице, внутри `t.Run` — те же три блока.
- Тестовые данные собираются функцией-фабрикой (`validRecording()`), а не общей мутируемой переменной.

## Общие правила

- TypeScript strict, без `any`. Идентификаторы на английском, комментарии и тексты интерфейса на русском.
- В записи сборок и в репозиторий не должны попадать ключи, токены, пароли, адреса серверов и личные данные. Сырые журналы лежат в `recordings/raw/` и в git не идут. Исключение — учётка локальной базы в `compose.yaml` и `.devcontainer/compose.yaml`: она только для разработки, порты привязаны к 127.0.0.1, в продакшене пароли берутся из `.env` на сервере.
- Небольшие коммиты в формате [Conventional Commits](https://www.conventionalcommits.org/en/v1.0.0/): `<тип>(<область>): <описание>`. Тип и область на английском (`feat`, `fix`, `docs`, `test`, `refactor`, `ci`, `chore`, `build`), описание того, что сделано, — на русском: `feat(core): добавлен проигрыватель записи`. Области: `core`, `web`, `api`, `deploy`, `ci`. Ломающие изменения — `!` после типа и футер `BREAKING CHANGE:`.
