# Киберзавод

Сайт-витрина: цех в браузере (вид сверху) проигрывает записи того, как ИИ-агенты собирают этот же проект. Код открытый, сайт для портфолио. Домен — cyberzavod.com.

Правила конкретных частей лежат рядом с кодом: `apps/web/CLAUDE.md`, `apps/api/CLAUDE.md`, `packages/core/CLAUDE.md`, `packages/recorder/CLAUDE.md`.

## Команды

- `make check` — все проверки: типы, тесты, сборка фронта и API, сборка Docker-образа. CI вызывает те же make-цели. Должна проходить перед любым коммитом.
- `make dev` — Postgres и API в Docker, фронт с горячей перезагрузкой на http://localhost:4321.
- `make up` / `make down` — поднять или остановить Docker-окружение.
- `make server-bootstrap` — привести VPS к состоянию из `deploy/` (идемпотентно, нужен SSH-алиас `cyberzavod`).
- `make format` — привести код к стилю (Prettier, ESLint --fix, gofumpt, goimports).
- `/feature <номер issue>` — провести задачу через цех агентов: постановка (ждёт одобрения человека), код, проверки, ревью, выкатка.
- `/publish-recording` — опубликовать запись сборки: черновик из журнала, чистовая редактура промптов и реплик, проверка человеком, файл в `recordings/published/`.
- `make project-init DIR=<путь> ID=<id> [VERSION=<версия>]` — подключить внешний git-репозиторий к заводу (см. «Playbooks завода»).
- `make help` — остальные команды.

Если работаешь в dev-контейнере (`DEVCONTAINER=true`, см. `.devcontainer/README.md`): Docker и доступа к серверу там нет намеренно. Перед коммитом — `make check-web check-api`, проверки с Docker выполнит CI. API — `make api-dev`, сайт — `pnpm dev --host`.

## Устройство

Монорепозиторий: pnpm workspaces для TypeScript, отдельный Go-модуль для API.

- `packages/core` — ядро завода на чистом TypeScript: формат записи сборки, счётчики, проигрыватель (сценарий цеха и кадр в любой момент).
- `packages/recorder` — запись сборок: хуки Claude Code пишут сырой журнал, `make recording-draft` собирает из него черновик, `make recording-publish` превращает отредактированный черновик в запись формата ядра.
- `recordings/` — `raw/` (сырые журналы) и `drafts/` (черновики с исходными текстами промптов) вне git; `published/` — опубликованные записи в git, сайт берёт их при сборке.
- `.cyberzavod/project.json` — конфиг проекта: `id`, версия завода `factory` и `checks` (команда проверок и каталоги с кодом для хука остановки); сборка несёт в записи `id` и `factory`.
- `projects/` — карточки проектов для сайта (название, описание, ссылки), в git; сайт берёт их при сборке.
- `factory/` — подключение внешних проектов: `project-init.sh` (его запускает `make project-init`), шаблон их настроек Claude Code `project-settings.json` и тест `project-init.test.sh`.
- `apps/web` — сайт: Astro + SolidJS + Nano Stores, слои FSD, свой ui-kit на Kobalte, цех на весь экран на canvas через PixiJS.
- `apps/api` — API на Go с Postgres.
- `compose.yaml` — локальное окружение: db → migrate → api.
- `deploy/` — продакшен: compose для сервера, nginx на хосте, скрипты деплоя и бэкапа. Как это работает — `deploy/README.md`.

Деплой автоматический: push в `main` → проверки → образы в GHCR с тегом sha → выкатка на сервер. Всё, что настроено на сервере, описано в `deploy/`; руками на сервере ничего не меняем.

## Хуки Claude Code (`.claude/settings.json`)

- **Запись:** каждое событие сессии (промпт, вызов инструмента, сабагент, остановка) асинхронно дописывается в `recordings/raw/<сессия>.jsonl` от `CYBERZAVOD_HOME`, а если он не задан, от `CLAUDE_PROJECT_DIR`. Начало сессии несёт проект и версию завода из `.cyberzavod/project.json`. Журналы вне git; в запись для сайта попадают только этапы, счётчики, промпты и реплики в чистовом виде (цель и требования, строка над говорящим и полный текст) — после проверки человеком.
- **Остановка:** команду проверок и каталоги с кодом хук берёт из `checks` в `.cyberzavod/project.json`. У Киберзавода это `make check-web check-api` и `apps`, `packages`. Если агент в этом ходе менял код в этих каталогах, он не может закончить, пока команда красная; без `checks.paths` хук следит за всем репозиторием, без `checks` или без конфига ничего не проверяет, а при битом конфиге отпускает агента с сообщением; после трёх неудачных попыток подряд останавливается и зовёт человека. Чужие незакоммиченные правки, сделанные до хода, агента не держат: в начале хода `turn-start.sh` запоминает отпечаток кода.
- **Облако:** в облачной сессии Claude Code (`CLAUDE_CODE_REMOTE=true`) `session-start.sh` на старте и при возобновлении ставит зависимости pnpm и, если нужно, пересобирает golangci-lint: версия — из `GOLANGCI_LINT_VERSION` в `.devcontainer/Dockerfile`, Go — из `apps/api/go.mod`. Без этого образ облака не проходит `make check-web check-api`, и остановка не отпускает агента. Локально и в dev-контейнере хук ничего не делает.
- **Go:** после правки `.go`-файл форматируется `golangci-lint fmt` (gofumpt и goimports), как в `make check-api`.
- **Запреты:** инструментам чтения и правки закрыты `.env`, правке — сырые журналы (`permissions.deny`). Команды Bash эти правила не перекрывают: `.env` всё равно не читать.

Цех рисует только то, что выводится из событий записи через сценарий ядра. Новое визуальное состояние начинается с нового типа события в `packages/core`.

## Playbooks завода

Набор, который завод отдаёт проектам; `make project-init` копирует его во внешний проект без правок:

- агенты `.claude/agents/analyst.md`, `coder.md`, `tester.md`, `reviewer.md`;
- скилл `.claude/skills/feature/SKILL.md`;
- хуки остановки `.claude/hooks/stop-gate.sh`, `turn-start.sh` и общий `lib.sh`;
- шаблон настроек проекта `factory/project-settings.json`: хуки записи и остановки, запреты на `.env`. Он становится `.claude/settings.json` проекта, а не копируется как есть.

Список набора записан в трёх местах и меняется во всех: здесь, в `PLAYBOOKS` скрипта `factory/project-init.sh` (шаблон — там же, в `SETTINGS_TEMPLATE`) и в `PLAYBOOK_FILES` теста `factory/project-init.test.sh` (тест намеренно сверяет скрипт с отдельным списком).

Только у завода остаются `format-go.sh`, `session-start.sh`, агент `recording-editor`, скилл `publish-recording` и тесты хуков.

Правило: файлы набора не называют проект, его команды и каталоги. Всё, что зависит от проекта, они берут из `checks` в `.cyberzavod/project.json` и из CLAUDE.md проекта.

От CLAUDE.md проекта набор ждёт:

- команды форматирования, быстрых проверок и полных проверок (нет команды форматирования — шаг пропускается);
- правила кода и тестов: по ним пишет исполнитель, проверяют тестировщик и ревьюер.

Версия набора — тег `factory-v<версия>` в репозитории завода; проект получает файлы из тега, а не из рабочей копии. Выпуск версии: правка набора, затем `factory` в `.cyberzavod/project.json` завода, затем тег `factory-vX.Y.Z` на этом коммите и `git push origin factory-vX.Y.Z`.

Подключение проекта: `make project-init DIR=<путь к корню git-репозитория> ID=<id> [VERSION=<версия>]`. Без `VERSION` берётся старший тег; `VERSION` читается только из командной строки make, не из окружения, и должен быть точным именем тега без `factory-v`. Команда кладёт набор, `.claude/settings.json` из шаблона и `.cyberzavod/project.json` (`id`, `factory`) в проект и заготовку карточки `projects/<id>.json` в завод. Если в проекте или в заводе уже есть что-то из этого, команда отказывает и ничего не меняет. Остальное делает человек, команда напоминает об этом в конце:

- создать `.claude/settings.local.json` проекта с `{"env": {"CYBERZAVOD_HOME": "<путь к заводу>"}}` и не коммитить его: по этой переменной хуки записи находят завод, без неё не пишут ничего;
- заполнить `checks` в `.cyberzavod/project.json`;
- написать CLAUDE.md проекта;
- заполнить `description`, `repo`, `website` в `projects/<id>.json` и закоммитить карточку в заводе.

Набору нужны `jq` и `git`. Без `jq` хуки остановки ничего не проверяют: `stop-gate.sh` отпускает агента с сообщением, `turn-start.sh` молча выходит.

## Модели и расход

- Станции `/feature` — агенты в `.claude/agents/`, у каждого во frontmatter своя модель и effort: постановка и ревью — Opus, код и проверки — Sonnet. Редактор реплик `recording-editor` (`/publish-recording`) — Sonnet на среднем effort. Повторная доработка переходит на Opus, после третьего возврата пайплайн зовёт человека. Возвраты станций попадают в запись сборки, возвраты по CI и проверке сайта — нет. Новая роль — новый агент со своей моделью.
- Сабагенты без своей модели, например general-purpose, работают на Sonnet (`CLAUDE_CODE_SUBAGENT_MODEL`). Встроенные Explore и Plan наследуют модель сессии. Effort проекта — `high`, контекст сжимается на 400 тыс. токенов (`.claude/settings.json`).
- Больше всего стоит длинный контекст, а не модель: каждый запрос заново читает всю историю. Одна задача — одна сессия; объёмную работу — агентам со свежим контекстом.

## Качество кода

Код должен читаться как описание того, что он делает, и расширяться добавлением, а не правкой по всему проекту. Конкретно:

- **Имена из предметной области.** Запись, сборка, этап, цех, возврат — а не `data`, `item`, `handle`, `process`. Без сокращений, кроме общепринятых (`ctx`, `err`, `id`).
- **Одна функция — одно действие.** Если функцию нельзя назвать без «и», её надо разделить. Тело читается сверху вниз без прыжков: сначала ранние выходы, потом основной путь.
- **Расширение через типы, а не через условия.** Новый вариант — новый член размеченного объединения (TS) или новая реализация интерфейса (Go). Ветвление по варианту — исчерпывающий `switch`, где пропущенный случай ловит компилятор, а не цепочка `if` по строкам в разных файлах.
- **Абстракция — когда появился второй реальный случай.** Не заводить интерфейс, фабрику или параметр «на будущее».
- **Зависимости направлены внутрь.** Ядро ничего не знает о сайте и API; бизнес-логика не знает о фреймворке, базе и HTTP — только об интерфейсах.
- **Ошибки не глотаются.** Либо обработать, либо вернуть с контекстом (`fmt.Errorf("загрузка миграций: %w", err)`, свой класс ошибки в TS).
- **Комментарий объясняет «почему»**, когда это не видно из кода. Пересказ кода словами, закомментированный и мёртвый код не допускаются.
- **Без магических значений.** Числа и строки со смыслом получают имя.

## Стиль кода

Проверяется инструментами: `make check` падает при нарушении, `make format` приводит код к стилю.

- **TypeScript:** Prettier (ширина 100, двойные кавычки, точки с запятой, запятые в конце списков) и ESLint (typescript-eslint strict и stylistic, Solid, Astro, JSDoc, Vitest).
- **JSDoc** — на всём экспортируемом: функции, компоненты, классы, типы, интерфейсы, константы. Одно-два предложения о том, что это и зачем, без описания реализации. У функций — `@param` на каждый параметр, `@returns`, и `@throws`, если функция бросает ошибку; у `@param` и `@returns` тип в фигурных скобках: `@param {number} ms Длительность в миллисекундах.` Тип в JSDoc должен совпадать с сигнатурой TypeScript — линтер проверяет только его наличие, совпадение проверяет ревьюер.
- **Go:** golangci-lint (staticcheck, errcheck, revive, gofumpt, goimports). Doc-комментарий — на каждом экспортируемом идентификаторе и на пакете; начинается с имени, дальше по-русски: `// Load читает настройки из окружения.` Неэкспортируемое — по желанию, когда имя не говорит само за себя.
- Комментарии внутри кода — только «почему».

## Тесты

- Новая логика — с тестом рядом.
- **TypeScript — Vitest.** Каждая группа тестов — в `describe` с именем проверяемой функции или компонента, внутри — `it` с поведением по-русски: `describe("parseRecording")` → `it("отклоняет неизвестный этап")`. Тест вне `describe` — ошибка линтера.
- **Go — стандартная библиотека.** `TestXxx` на проверяемую функцию, случаи — таблицей, каждый в `t.Run`; проверки через `if` и `t.Fatalf` с понятным сообщением.
- **Arrange / Act / Assert** — три блока, разделённые пустой строкой, без комментариев-меток. Если готовить нечего, блока Arrange нет.
- Act — одно действие над проверяемым кодом. Для исключения: `const act = () => parse(raw);`, затем `expect(act).toThrow(…)`.
- Тестовые данные собираются фабрикой (`validRecording()`), а не общей мутируемой переменной.
- Shell-тесты хуков и деплоя — по тем же правилам: функция на сценарий, блоки через пустую строку.

`make format` выполняет Prettier, затем ESLint --fix и снова Prettier: автоисправления ESLint (например, скобки у условий) форматируются в стиле Prettier.

## Задачи

План работ — [GitHub Issues](https://github.com/bysavelii/cyberzavod/issues): одна задача — один issue с тем, зачем она, что сделать и когда готово. Коммит, который её закрывает, пишет в теле `closes #N`.

## Общие правила

- TypeScript strict, без `any`. Идентификаторы на английском, комментарии и тексты интерфейса на русском.
- В записи сборок и в репозиторий не должны попадать ключи, токены, пароли, адреса серверов и личные данные. Сырые журналы лежат в `recordings/raw/` и в git не идут. Исключение — учётка локальной базы в `compose.yaml` и `.devcontainer/compose.yaml`: она только для разработки, порты привязаны к 127.0.0.1, в продакшене пароли берутся из `.env` на сервере.
- Небольшие коммиты в формате [Conventional Commits](https://www.conventionalcommits.org/en/v1.0.0/): `<тип>(<область>): <описание>`. Тип и область на английском (`feat`, `fix`, `docs`, `test`, `refactor`, `ci`, `chore`, `build`), описание того, что сделано, — на русском: `feat(core): добавлен проигрыватель записи`. Области: `core`, `recorder`, `recordings`, `web`, `api`, `deploy`, `ci`, `hooks`, `factory`. Ломающие изменения — `!` после типа и футер `BREAKING CHANGE:`.
