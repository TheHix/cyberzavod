# Киберзавод

Сайт-витрина: изометрический цех в браузере проигрывает записи того, как ИИ-агенты собирают этот же проект. Код открытый, сайт для портфолио. Домен — cyberzavod.com.

## Команды

- `make check` — все проверки: типы, тесты, сборка фронта и API, сборка Docker-образа. CI вызывает те же make-цели. Должна проходить перед любым коммитом.
- `make dev` — Postgres и API в Docker, фронт с горячей перезагрузкой на http://localhost:4321.
- `make up` / `make down` — поднять или остановить Docker-окружение.
- `make help` — остальные команды.

## Устройство

Монорепозиторий: pnpm workspaces для TypeScript, отдельный Go-модуль для API.

- `packages/core` — ядро завода на чистом TypeScript: формат записи сборки, счётчики, дальше проигрыватель. Ни DOM, ни фреймворков, ни зависимостей. Тесты — `node --test`.
- `apps/web` — сайт: Astro + SolidJS, слои FSD. Страницы собираются в статический HTML; JS получают только островки с `client:*`. Цех будет рисоваться на canvas через PixiJS.
- `apps/api` — Go: `cmd/api` (подкоманды `serve`, `migrate`, `healthcheck`), `internal/*`, SQL-миграции goose в `migrations/`. Все маршруты под `/api`.
- `compose.yaml` — локальное окружение: db → migrate → api.

Цех рисует только то, что выводится из событий записи. Новое визуальное состояние начинается с нового типа события в `packages/core`.

## Правила фронта (FSD)

- Слои в `apps/web/src`: `app` → `pages` → `widgets` → `features` → `entities` → `shared`. Импорт только из слоёв ниже своего.
- `src/pages` — маршруты Astro, они же слой pages: только компоновка виджетов, без логики. Единственное исключение из направления импортов: страницы подключают layout из `app/layouts`, потому что маршрутизация в Astro живёт в `pages`.
- Слайс наружу отдаёт только то, что есть в его `index.ts`; глубокие импорты в чужой слайс запрещены.
- Логика, которую можно написать без браузера, идёт в `packages/core` или `shared/lib` и покрывается тестом.
- Компоненты интерфейса — Solid (`.tsx`), статичная разметка — `.astro`. Директиву `client:*` ставить только там, где нужна интерактивность.
- Импорты между слоями и слайсами — через `@/…`, внутри слайса — относительные. Публичный API слайса подключается по папке (`@/widgets/build-stats`), отдельные файлы — с расширением `.ts`/`.tsx`. Код, который тестируется через `node --test` (`shared/lib`), импортирует только относительно: Node не знает про `@/`.

## Правила API

- Хендлеры зависят от интерфейсов (`Pinger` и т. п.), а не от `pgxpool` напрямую, чтобы тестироваться без базы.
- Изменение схемы — только новой миграцией `NNNNN_описание.sql`; применённые миграции не редактировать.
- Логи — `slog` в JSON; конфигурация — только из переменных окружения.

## Общие правила

- TypeScript strict, без `any`. Идентификаторы на английском, комментарии и тексты интерфейса на русском.
- Новая логика — с тестом рядом.
- В записи сборок и в репозиторий не должны попадать ключи, токены, пароли, адреса серверов и личные данные. Сырые журналы лежат в `recordings/raw/` и в git не идут. Исключение — учётка локальной базы в `compose.yaml`: она только для разработки, порты привязаны к 127.0.0.1, в продакшене пароли берутся из `.env` на сервере.
- Небольшие коммиты в формате [Conventional Commits](https://www.conventionalcommits.org/en/v1.0.0/): `<тип>(<область>): <описание>`. Тип и область на английском (`feat`, `fix`, `docs`, `test`, `refactor`, `ci`, `chore`, `build`), описание того, что сделано, — на русском: `feat(core): добавлен проигрыватель записи`. Области: `core`, `web`, `api`, `deploy`, `ci`. Ломающие изменения — `!` после типа и футер `BREAKING CHANGE:`.
