## Как это устроено

Завод — это репозиторий Киберзавода. Он делает две вещи: отдаёт проекту набор агентов и хуков и записывает, как Claude Code ведёт в проекте задачу. Хуки Claude Code пишут журнал сессии в каталог `recordings/raw/` клона завода. Из журнала собирается запись: этапы, промпты, реплики станций, время и токены. Запись публикуется на сайте, а цех её проигрывает.

Дальше по шагам: подготовить инструменты, подключить проект командой, сделать четыре ручных шага, провести задачу через `/feature` и опубликовать запись через `/publish-recording`. В конце — живой пример, чужой проект, который уже подключён.

## Что нужно

- Claude Code.
- `git` и `jq`. Без `jq` хуки остановки ничего не проверяют: `stop-gate.sh` отпускает агента с сообщением, а `turn-start.sh` молча выходит. Команде подключения нужен ещё `tar`.
- `gh` — GitHub CLI: его вызывают `/feature` и станции пайплайна.
- Node 24 или новее и pnpm: версия Node задана в `engines` корневого `package.json` завода. Хук записи запускает `packages/recorder/src/bin/record.ts` через `node` из клона завода.
- Клон завода с тегами и установленные зависимости. Набор для проекта берётся из тега `factory-v<версия>`, а `git clone` забирает теги сам:

```bash
git clone https://github.com/bysavelii/cyberzavod.git /путь/к/cyberzavod
cd /путь/к/cyberzavod
pnpm install
git tag --list 'factory-v*'
```

Последняя команда должна напечатать хотя бы один тег. Сам проект — обычный git-репозиторий с GitHub-задачами (issues), у которого есть команды проверок.

## Подключить проект командой

Из корня клона завода:

```bash
make project-init DIR=/путь/к/проекту ID=my-project
```

`DIR` — корень git-репозитория проекта, `ID` — идентификатор проекта: латинские буквы, цифры, `-` и `_`. По нему проект называется в записях, и он же становится частью адреса его страницы, `/projects/<id>/`.

Версия набора. Без `VERSION` берётся старший тег `factory-v*` (по номеру, а не по алфавиту: `0.10.0` новее `0.9.0`). Чтобы взять другую, укажите точное имя тега без `factory-v`:

```bash
make project-init DIR=/путь/к/проекту ID=my-project VERSION=0.2.0
```

`VERSION` читается только из командной строки make, переменную окружения команда не учитывает: одноимённая переменная других инструментов молча выбрала бы чужую версию.

Что появляется в проекте:

- агенты станций `.claude/agents/analyst.md`, `coder.md`, `tester.md` и `reviewer.md`;
- скилл `.claude/skills/feature/SKILL.md` — команда `/feature`;
- хуки остановки `.claude/hooks/stop-gate.sh`, `turn-start.sh` и общий `lib.sh`;
- `.claude/settings.json` из шаблона `factory/project-settings.json`: хуки записи и остановки и запрет читать и править `.env` и `.env.*`;
- `.cyberzavod/project.json` с двумя полями: `id` и `factory` (версия набора).

Что появляется в заводе: заготовка карточки `projects/<id>.json` с названием, равным `id`, и описанием «Описание проекта ещё не заполнено.».

Все файлы набора берутся из тега, а не из рабочей копии завода: проект получает выпущенную версию, а в записи сборки по `factory` видно, какой набор работал.

Все проверки идут до первой записи. Если что-то не так (нет тега, `DIR` не корень git-репозитория, неверный `ID`), команда печатает причину и ничего не создаёт: исправьте и запустите снова. Если в проекте уже есть `.cyberzavod`, `.claude/settings.json`, любой файл набора или в заводе уже есть карточка `projects/<id>.json`, команда отказывает, ничего не меняет и печатает список этих путей и команды для переноса вручную. Уже подключённый проект команда не обновляет: новую версию набора переносят руками.

В конце команда печатает, что осталось сделать вам (здесь вместо путей заглушки):

```text
Проект my-project подключён к заводу, версия 0.2.0.

Осталось сделать вам:
  1. Создайте /путь/к/проекту/.claude/settings.local.json и не коммитьте его (добавьте в .gitignore проекта):
       {"env": {"CYBERZAVOD_HOME": "/путь/к/cyberzavod"}}
  2. Заполните checks в /путь/к/проекту/.cyberzavod/project.json: команду проверок и каталоги с кодом.
  3. Напишите CLAUDE.md проекта: команды форматирования, быстрых и полных проверок, правила кода
     и тестов (см. «Playbooks завода» в CLAUDE.md завода).
  4. Заполните description, repo, website в /путь/к/cyberzavod/projects/my-project.json и закоммитьте карточку в заводе.
```

## Четыре ручных шага

### 1. Путь к заводу

Создайте в проекте `.claude/settings.local.json`:

```json
{ "env": { "CYBERZAVOD_HOME": "/путь/к/cyberzavod" } }
```

и добавьте `.claude/settings.local.json` в `.gitignore` проекта: путь у каждого свой, коммитить его не нужно. По этой переменной хуки записи находят завод. Если её нет, они молча выходят и журнал не пишется.

### 2. Проверки

Откройте `.cyberzavod/project.json` проекта и допишите `checks`. Вот файл Personal Finance Lab, проекта, который уже подключён к заводу:

```json
{
  "id": "personal-finance-lab",
  "factory": "0.1.0",
  "checks": {
    "command": "pnpm check",
    "paths": ["src"]
  }
}
```

- `command` — команда проверок. Хук остановки запускает её, когда агент в этом ходе менял код. Пока она красная, агент не может закончить ход. Она идёт на каждой остановке, поэтому в неё не кладут то, что требует недоступной агенту среды, например Docker: это оставляют CI.
- `paths` — каталоги с кодом. Хук следит только за ними: правки вне этих каталогов проверку не запускают. Без `paths` хук следит за всем репозиторием.
- Без `checks` (или без `command` внутри) хук остановки ничего не проверяет. Если `.cyberzavod/project.json` не читается, хук отпускает агента с сообщением.

Чужие незакоммиченные правки, сделанные до хода, агента не держат: в начале хода `turn-start.sh` запоминает отпечаток кода.

### 3. CLAUDE.md проекта

От CLAUDE.md проекта набор ждёт:

- команды форматирования, быстрых проверок и полных проверок; если команды форматирования нет, этот шаг пропускается;
- правила кода и тестов: по ним пишет исполнитель, а проверяют тестировщик и ревьюер.

Сами файлы набора не называют проект, его команды и каталоги: всё, что от проекта зависит, они берут из `checks` и из CLAUDE.md проекта. Исполнитель форматирует код командой из CLAUDE.md, потом запускает `checks.command`, а если `checks` нет, быстрые проверки из CLAUDE.md.

Так выглядит раздел с командами в CLAUDE.md у Personal Finance Lab:

```markdown
## Commands

- `pnpm dev` — dev server on http://localhost:5173.
- `pnpm format` — Prettier, ESLint `--fix`, Prettier again.
- Fast checks: `pnpm lint && pnpm typecheck && pnpm test`.
- Full checks: `pnpm check` — formatting, lint, types, tests and production build. CI runs the
  same command; it must pass before every commit.
```

Полные проверки здесь совпадают с `checks.command` из шага 2.

### 4. Карточка проекта

Откройте в заводе `projects/<id>.json`, заполните его и закоммитьте в заводе:

- `name` — название проекта для сайта;
- `description` — описание одной строкой, непустое;
- `repo` и `website` — необязательные ссылки, только с `https`. Другая схема или пустая строка не пройдут проверку.

Битая карточка роняет сборку сайта. Образец — карточка Personal Finance Lab, [`projects/personal-finance-lab.json`](https://github.com/bysavelii/cyberzavod/blob/main/projects/personal-finance-lab.json): в ней `id`, `name`, `description` и `website`, без `repo`. Страница проекта появится на сайте как `/projects/<id>/`.

## Задача через цех: /feature

Откройте Claude Code в каталоге проекта, а не завода: хуки берут конфиг проекта оттуда, где идёт сессия. Задача — issue в репозитории проекта: зачем она, что сделать и когда готово. Запустите:

```text
/feature 12
```

Здесь `12` — номер issue. Перед стартом рабочая копия проекта должна быть чистой и на свежем `main`: пайплайн сам проверяет это через `git status` и `git pull --ff-only` и, если что-то не так, останавливается и спрашивает вас.

Дирижёр, то есть сама сессия, код не пишет, а передаёт работу станциям. Каждая станция — агент из `.claude/agents/` со своей моделью:

- постановка — `analyst`, Opus: ошибка в постановке обходится дороже всего;
- код — `coder`, Sonnet, а на второй доработке Opus;
- проверки — `tester`, Sonnet;
- ревью — `reviewer`, Opus: последний фильтр перед выкаткой.

Ход работы:

1. Постановка. `analyst` изучает код и пишет план с критериями готовности. Пайплайн показывает её целиком вместе с вопросами и ждёт вашего одобрения. Мелкие правки вносит сам, для крупных зовёт `analyst` заново. Одобренную постановку он публикует комментарием в issue.
2. Код. `coder` делает задачу по постановке.
3. Проверки. `tester` сверяет результат с критериями. Дефект — возврат.
4. Ревью. `reviewer` читает изменения. «На доработку» — возврат, «Принято» — выкатка.
5. Выкатка. Коммиты по областям, у последнего в теле `closes #12`, затем `git push`. Дальше работает CI вашего проекта: пайплайн ждёт его результата. Если менялся интерфейс, он открывает страницу в браузере. Красный CI — тоже возврат.

### Возвраты

Возвраты от проверок, ревью, CI и сайта считаются вместе и образуют лестницу:

1. первый возврат — `coder` на своей модели, Sonnet;
2. второй — `coder` на Opus: Sonnet уже не справился дважды;
3. третий — стоп: пайплайн показывает оставшиеся замечания и что уже пробовали и зовёт вас.

На доработку `coder` получает постановку, замечания всех прошлых кругов и отчёт своей прошлой попытки. В запись сборки попадают только возвраты станций, возвраты по CI и проверке сайта — нет.

### Хук остановки

Пока `checks.command` красная и агент менял код в этом ходе, хук остановки не даёт ему закончить ход. После трёх неудачных попыток подряд он останавливается и зовёт человека.

Если пайплайн должен остановиться на вопросе к вам или на третьем возврате, а проверки красные, он прячет попытку: `git stash push --include-untracked -m "feature #12: что не так"`. Рабочая копия становится чистой, и хук отпускает. Когда вы ответите, первым делом пайплайн возвращает попытку через `git stash pop`. Если остановка финальная, попытка остаётся в stash, и пайплайн скажет об этом.

## Опубликовать запись: /publish-recording

Скилл `/publish-recording` есть только у завода, поэтому запускайте Claude Code в клоне завода, а не в проекте. Журнал проекта лежит там же, в `recordings/raw/<сессия>.jsonl`. Он вне git: до публикации ничего не уходит на сайт.

Черновик собирает `make recording-draft`. Без аргументов он берёт самый свежий по времени изменения журнал, а это может оказаться журнал текущей сессии в заводе, а не журнал вашего проекта. Поэтому укажите журнал явно (имя файла — идентификатор сессии, список по свежести — `ls -t recordings/raw`):

```bash
make recording-draft RAW=recordings/raw/<сессия>.jsonl
```

Скилл проведёт по шагам:

1. Черновик ложится в `recordings/drafts/<id>.json`, тоже вне git. В нём исходные тексты ваших промптов.
2. Редактура. Сессия пишет заголовок записи и переписывает ваши промпты в чистовой вид: главное указание и уточнения. Агент `recording-editor` пишет реплики станций и мастера и вмешательства человека, то есть моменты, когда автоматика ждала вашего слова. Если у сборки пусты `project` и `factory`, их заполняют по `id` и `factory` из `.cyberzavod/project.json` проекта.
3. Проверка человеком. Скилл показывает таблицы: сборки, промпты, реплики и вмешательства. Читайте их внимательно: на сайт уйдёт то, что вы одобрите. Публикация ищет в тексте адреса и ключи, но это лишь страховка.
4. Публикация:

```bash
make recording-publish
```

Команда проверяет формат записи и пишет `recordings/published/<id сборки>.json`. Если сборок несколько, `make recording-publish BUILD=<id сборки>` публикует только одну.

Посмотреть запись локально можно, запустив в клоне завода `pnpm dev`: сайт откроется на `http://localhost:4321`, запись будет по адресу `/recordings/<id>/`. Карточка проекта из шага 4 нужна и здесь: запись проекта без карточки роняет сборку сайта.

Если в одной сессии шло несколько задач, например несколько `/feature`, каждая публикуется отдельной записью. Первая сборка получает `id` черновика, остальные — `<id>-2`, `<id>-3` и так далее. Скилл разметит их в черновике сам: у каждой сборки свой проект, версия набора, заголовок и список запусков станций (`runs`), а промпт, с которого началась задача, отмечается полем `build`.

### Как запись попадёт на cyberzavod.com

Сайт берёт записи и карточки проектов при сборке, а выкатка идёт после попадания в `main` завода. Поэтому предложите pull request в [репозиторий завода](https://github.com/bysavelii/cyberzavod): карточка `projects/<id>.json` и запись `recordings/published/<id сборки>.json`. Перед этим запустите в клоне `make check-web`: он собирает сайт и ловит битую карточку или запись.

## Если что-то не работает

- Журнал не пишется. Проверьте `.claude/settings.local.json` проекта: без `CYBERZAVOD_HOME` хуки молча выходят. И сделан ли `pnpm install` в заводе: хук записи запускает скрипт из клона завода, ему нужны зависимости.
- Хуки подключили посреди сессии. В журнале нет `session_start`, поэтому у сборки пусты `project` и `factory`. Их заполняют на шаге 2 публикации, но проще начать новую сессию.
- Хук остановки не отпускает. Значит, красная `checks.command`: исправьте то, что она печатает. После трёх неудачных попыток подряд хук сам остановится и позовёт человека. Без `jq` или при битом `.cyberzavod/project.json` он отпускает агента с сообщением и ничего не проверяет.
- Нужна другая версия набора. Версия — тег `factory-vX.Y.Z` в заводе, её задаёт `VERSION`. Подключённый проект команда не обновляет: для переноса она печатает команды.

## Живой пример

Personal Finance Lab — проект, уже подключённый к заводу: [страница проекта](/projects/personal-finance-lab/), его `id` — `personal-finance-lab`, версия набора — `0.1.0`. Из его файлов взяты примеры выше.

Запись [«Personal Finance Lab: финансовая лаборатория с нуля»](/recordings/2026-10-05-4365c610-2/) — вторая сборка своей сессии. Первая сборка той же сессии — запись `2026-10-05-4365c610` проекта `cyberzavod`. Так выглядят несколько сборок в одной сессии.

Все файлы набора и скрипт подключения лежат в репозитории завода: [`factory/project-init.sh`](https://github.com/bysavelii/cyberzavod/blob/main/factory/project-init.sh), [`.claude/skills/feature/SKILL.md`](https://github.com/bysavelii/cyberzavod/blob/main/.claude/skills/feature/SKILL.md) и раздел «Playbooks завода» в [CLAUDE.md](https://github.com/bysavelii/cyberzavod/blob/main/CLAUDE.md).
