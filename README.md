# Cyberzavod

Cyberzavod is a local-first, model-agnostic development harness for AI-assisted software projects.

**Your stack can change. Your AI can change. Cyberzavod keeps the development process consistent.**

Cyberzavod owns the development process, not the technology stack. It does not write code and it is not an agent: it gives the agent you already use a process to follow, checks that the work is green before the agent stops, and keeps a journal of sessions and decisions next to your project.

The site [cyberzavod.com](https://cyberzavod.com) is the visual side: a top-down factory floor that replays recorded sessions, where AI agents built this very repository.

## The problem

AI coding agents are fast, but every project, model and tool ends up with its own prompts, its own rules files and its own habits. Change the model or the agent, and the process goes with it. Nothing records why the work went the way it did.

Cyberzavod keeps three things stable while everything around them changes:

- **The process.** Task → Plan → Implement → Review → Verify → Record, with a role per stage, shared engineering principles and a human approving the plan.
- **The checks.** A per-project list of verification commands. The agent cannot finish a turn that changed code while they are red.
- **The record.** A journal of sessions, decisions and notes in one plain JSON format that works for any agent.

Stack details (language, framework, package manager) are detected for convenience. They are metadata, not constraints.

## Run it

You need Node 22+ and git, on Linux, macOS or Windows. From the root of any project:

```bash
npx cyberzavod init
```

That is the only time npm is involved. `init` puts the whole tool, a single dependency-free file, into your project as `.cyberzavod/bin/cyberzavod.mjs`. The agent's hooks and every later command run that file with plain `node`, so there is nothing to install globally and no clone of this repository.

The wizard detects the project: languages, frameworks, package manager, git and scripts. It then proposes the project id, the workflow (`default`), an agent for each stage (currently Claude Code, model `default`), the verification commands and the journal location. Every answer has a default; `init --yes` takes them all.

Other commands:

| Command | What it does |
|---|---|
| `cyberzavod sync [--check] [--force]` | Regenerate the agent files and the vendored CLI; `--check` only reports what is stale |
| `cyberzavod status` | Project, workflow, stage agents, checks and journal |
| `cyberzavod decision "<what>" --why "<why>"` | Record a decision in the journal |
| `cyberzavod note "<text>"` | Record a note in the journal |
| `cyberzavod draft` / `cyberzavod publish` | Turn a captured agent session into a reviewed session record |

Inside a connected project, run them as `node .cyberzavod/bin/cyberzavod.mjs <command>`. To move to a newer release, run `npx cyberzavod@latest sync`: it rewrites the vendored CLI and the generated files.

## What `init` creates

In your project:

- `.cyberzavod/bin/cyberzavod.mjs`: the tool itself, committed so that every clone of your project has working hooks.
- `.cyberzavod/project.json`: the marker and config. It holds the project id, harness version, workflow, journal path, `agents.{stage}: {provider, agent, model}`, `verification.commands` and `verification.paths`, plus the detected stack.
- `AGENTS.md`: your project rules, written for any agent and for people. An existing hand-written `CLAUDE.md` is moved here.
- Files for the chosen agent, generated by an adapter. For Claude Code:
  - a thin `CLAUDE.md` entrypoint;
  - stage agents in `.claude/agents/`;
  - the `/feature` and `/publish-recording` skills;
  - hooks in `.claude/settings.json`, which run `node .cyberzavod/bin/cyberzavod.mjs hook …` and need only Node and git.
- A `.gitignore` line for the journal's `capture/` directory.

Generated files carry a "generated by `cyberzavod sync`" mark. `sync` overwrites only those files and refuses to touch yours.

## The workflow

`/feature <task>` in the agent runs the default workflow:

1. **Task:** a description, link or tracker id; `AGENTS.md` says how to read it.
2. **Plan:** the planning role studies the code and writes a plan with acceptance criteria. A human approves it.
3. **Implement:** the implementation role makes the change and runs the checks.
4. **Review:** the review role reads the diff against the plan and the project rules.
5. **Verify:** the verification role confirms each criterion and runs the checks.
6. **Record:** commits follow the project's rules. Decisions and notes go to the journal, and the session can be published as a record.

Returns from review or verification go back to implementation: the second return uses a stronger model, and the third calls the human.

## What is stored locally

Everything stays on your disk; there is no server, account or telemetry.

- `.cyberzavod/project.json` and `.cyberzavod/bin/`: in the project, committed.
- The journal: by default `.cyberzavod/journal/` inside the project, so it travels with your repository. It can also live outside, for example `../<project>.cyberzavod/`.
  - `sessions/`, `decisions/` and `notes/` hold one JSON file per record. Each record has the envelope `{version, type, timestamp, projectId, sessionId, source, data}`.
  - `capture/` holds the adapter's raw session logs and drafts. It contains your original prompts and is never meant for git; `init` adds it to `.gitignore`.

The record format is the whole contract between the tool and any viewer. [cyberzavod.com](https://cyberzavod.com) is one such viewer; you can build your own on top of your journal.

## Repository layout

| Path | What it is |
|---|---|
| `harness/` | The process: principles, stages, workflows, conductor rules. Agent- and stack-neutral |
| `packages/core` | The model: records, project config, stages, harness |
| `packages/player` | The factory-floor player: script and frame of a session record; used only by the site |
| `packages/storage` | Disk: project config, the directory record store, harness loading |
| `packages/cli` | The `cyberzavod` npm package: the CLI, bundled with everything below into one file |
| `adapters/claude` | The Claude Code adapter: file generator, hooks, session capture |
| `.cyberzavod/` | This repository's own connection: config, vendored CLI and journal; the site is built from `.cyberzavod/journal/sessions/` |
| `apps/web` | The site: Astro, SolidJS, PixiJS factory floor |
| `apps/api` | The API: Go and Postgres |

The tool and the site share this repository but not code: the site only reads the record format. Releases go to npm when a `vX.Y.Z` tag is pushed.

Developing Cyberzavod itself: `pnpm install`, then `pnpm cyberzavod <command>` builds the CLI from source and runs it. `make dev` starts the site on http://localhost:4321 and the API, `make check` runs every check, and `make help` lists the rest. The project rules are in [AGENTS.md](AGENTS.md). There is an isolated dev container for AI agents; see [.devcontainer/README.md](.devcontainer/README.md).

A step-by-step guide to connecting a project is on the site: https://cyberzavod.com/guides/connect-project/ (source: [guides/connect-project.en.md](guides/connect-project.en.md), in Russian — [guides/connect-project.ru.md](guides/connect-project.ru.md)).
